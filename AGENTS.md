v# AGENTS.md — DRASTIC SMURF

## Project Overview

**Status:** Active development — core architecture complete, all four planned modules have working skeletons.  
**Goal:** An extensible desktop GUI for monitoring and interacting with multiple Elasticsearch clusters. Supports multiple clusters with separate credentials, a tabbed modular interface, and secure credential storage.

### Technology Stack

- **Rust** (edition 2024)
- **egui** + **eframe** (immediate-mode GUI, wgpu backend)
- **tokio** (async runtime)
- **reqwest** (async HTTP client)
- **serde/serde_json** (JSON parsing)
- **keyring** (OS-native secret storage)

Picking a preset (here or in God-mode) fills the body with the matching request examples from Elastic's OpenAPI specs under `####### EXAMPLE n: … #######` marker lines; when there are doc examples, the preset's own body becomes `EXAMPLE 0: Drastic Smurf preset` (otherwise it stays unmarked so it sends in one click). Sending while a marker remains opens a prompt: remove the example blocks and send, keep one example (no send), strip only the marker lines, or cancel. The body toolbar has "📌 Keep one ▾" and "🧹 Remove examples"; after removal "📖 Show examples" re-inserts them (tracked in `examples_source`, only while method and path are unchanged). Examples live in `assets/api_examples.json` (embedded with `include_str!`, logic in `src/modules/api_examples.rs`), regenerated by `scripts/gen_api_examples.py` from the ES and Kibana specs; it matches presets to spec operations by method and path, so re-run it after adding presets. The same file holds each preset's online API reference URL (`operation-<operationId>`, numeric ES variant suffix stripped, lowercased), shown as a clickable link in the preset hover card. |
| **God-mode Console** | ✅ Functional | Console fanned out across multiple selected clusters, run sequentially. A loop-values list (newline/comma, `('a','b')` style accepted) expands `{{loop_item}}` into one request per value per cluster; `{{cluster_name}}` and each target cluster's own Console variables are interpolated per job. Result extraction (one level of chaining): an expression of `&&`-joined dotted JSON paths (numeric segments index arrays; leading-dot keys via `indices..ds-x.policy`) is pulled from every response into an editable Extracted values list, one row per line with fields joined by ` && ` (`&&` is reserved). At most one `*` (a whole segment) per expression: every wildcard path must share the prefix before it, yielding one row per key/element; a path ending in `*` yields the key/index; non-wildcard paths repeat on every row. Missing/null, object, array, failed and non-JSON results become `null`/`object`/`array` fields with warnings. `{{results_item}}` (column 1) and `{{results_item.N}}` expand like loop values (clusters × loop × rows), substituted in a single pass after Console variables so response data is never re-interpolated. A request that uses `{{results_item…}}` never extracts, so it can't overwrite the list it reads. Runs over 200 requests ask for confirmation even for GET. Combined labelled response log (cluster, loop value, status, timing), dry run, confirm modal for multi-request writes, stop/stop-on-error, history, and global saved queries (`god_console_saved_queries` in `config.json`). Shares presets with the Console via `render_preset_list`. |

| **AI Assistant** | ✅ Functional | Side-dock chat panel for troubleshooting Elasticsearch and API usage. Streams from any OpenAI-compatible `/chat/completions` endpoint (OpenAI, Azure OpenAI, GitHub Copilot, Ollama, LM Studio, vLLM, OpenRouter, etc.). API keys stored in OS keyring, conversation history persisted in `config.json`, concise auto-injected cluster context (health/version/nodes/JVM/errors). SSE streaming with token-by-token UI updates and cancel support. Reasoning models' thinking (`delta.reasoning_content` / `delta.reasoning`) streams into a collapsible "💭 Thinking…" section on the reply (`ChatMessage::reasoning`, `#[serde(skip)]`, never sent back). `build_llm_messages` never sends empty turns (the streaming placeholder or a failed reply) and merges consecutive same-role turns: a trailing empty assistant turn makes some models (e.g. Gemma in LM Studio) stop instantly with no output. Mid-stream `{"error": …}` frames surface as errors; the SSE parser buffers bytes (UTF-8 safe) and accepts CRLF framing; the client uses a 180s read (idle) timeout instead of a total timeout. Blank replies are removed with an explanation (`finish_stream`), and conversations are saved when a reply finishes. **App access via tool calling** (`src/modules/assistant_tools.rs`, settings `tools_enabled` / `auto_run_reads`, both default on): tools `list_clusters`, `es_request`, `get_console`, `open_in_console` (loads, never sends) and `open_tab`. Each user message starts an `AgentRun`: stream → tool calls (assembled from streamed fragments in `llm.rs`) → host runs them in `DrasticSmurfApp::pump_assistant` every frame (dock open or not) → results appended as `tool` messages → next stream, capped at `MAX_TOOL_STEPS` (8). Only `es_request` with a non-GET/HEAD method (or any method when auto-run is off) waits for Approve/Decline in the chat; results are compacted and capped at 6000 chars. Tool calls without results (cancelled runs) are never sent; with tools off, tool turns are dropped. If the provider rejects tools, the request is retried without them and tools stay off for that model this session. Likewise, if it rejects `temperature` (OpenAI reasoning models accept only the default), the request is retried without it and temperature is omitted for that model this session (`retry_for` in `llm_assistant.rs`); settings also offer a "Model default" checkbox (`use_default_temperature`) that never sends it. HTTP failures go through `llm::describe_api_error`, which leads with a plain-language cause for quota/billing exhaustion (`insufficient_quota`), 429 rate limits and 401/403 key rejections before the provider's own message. The text-parsed consent cards (`parse_console_actions`) remain for replies without tool calls. |
| **Painless Playground** | ✅ Functional | Elasticsearch Painless script editor featuring preset templates (Math, Score, Filter, String manipulation), live JSON parameters validation, and full mock context indexing setup. |
| **Osquery** | ✅ Functional | Live Osquery queries through Kibana, targeted like Kibana's picker: debounced type-to-search agents (KQL wildcard on hostname/agent ID, scoped to Osquery-enabled policies) beside a Groups panel (All agents, platforms, Osquery policies, each with counts; platform values discovered exactly via public Fleet API), plus a filterable picker for Osquery saved queries (`saved_query_id`/ECS mapping sent only while the SQL is unedited). Requires the Osquery Manager integration and appropriate Kibana/Fleet privileges. |

### Packaging (requires release binary)

Windows MSI shortcuts (Start Menu and desktop) are defined in `wix/main.wxs`.
Both shortcuts and the Installed Apps entry use `wix/Product.ico`, generated
from a head crop of the app's `drastic.png` artwork. Shortcuts are removed on uninstall.
`assets/drastic-smurf.png` is the shared tray/window and Linux launcher icon.
Both DEB and RPM install it under the hicolor icon theme. Regenerate the PNG and
multi-resolution ICO with `python scripts/gen_icons.py` (requires Pillow).
Keep `"msi"` in cargo-dist's `allow-dirty` list so it preserves the customized
WiX template instead of rejecting or regenerating its shortcuts and icon.
The advertised shortcuts' icon identifier must end in `.exe` to match the
component's executable key file (WiX ICE50), even though its source is an ICO.
CI's Windows MSI job compiles the app and links the installer with validation enabled.

Linux builds require GTK 3 and Ayatana AppIndicator development packages in
addition to D-Bus, Wayland, xkbcommon, and pkg-config (see README.md). VS Code
Linux build tasks invoke `cargo` directly; `flatpak-spawn` is not required.

```bash
# Install packaging tools
$ cargo install --locked cargo-deb cargo-generate-rpm

# Debian/Ubuntu
$ cargo deb

# RHEL/Fedora
$ cargo generate-rpm
```

## Security Considerations

- **Do not commit credentials.** Passwords and API keys are stored in the OS keyring.
- Use `directories` crate for config storage (`~/.config/drastic-smurf/` on Linux).
- **Export JSON never contains passwords or API keys.** Exported cluster configs omit credentials; imported clusters require credential re-entry.
- Per-cluster cached module data (status history, tasks cache, snapshot cache, saved queries) is stored in `config.json` alongside cluster configs.
- Application state flags, including theme choices, VFX toggles, and onboarding tour status (`wizard_completed`), are persisted in `config.json`.
- TLS verification is on by default; per-cluster override available.
- Custom CA certificate support is partially implemented (`CaCert::Custom` works; `CaCert::Bundled` is a TODO).
- `ClusterConfig::auth_method` selects Basic (default for legacy configs) or ApiKey (base64 `encoded` key or raw `id:api_key`). Both use the existing `cluster:<name>` keyring credential slot; only the authentication method is persisted. `AuthMethod` writes snake_case values and accepts the earlier local `Basic`/`ApiKey` values. `EsClient::apply_auth` applies the selected auth to Elasticsearch and Kibana requests, marks API-key headers sensitive, and its Debug implementation omits credentials. Generic `token:` helpers in `auth.rs` remain unused.
- SSH tunnels are owned and shared by client clones, opened on demand, and reopened after process exit. Hostname targets preserve TLS verification; IP targets currently bypass certificate checks. A separate Kibana host is not tunnelled. Keep these boundaries explicit in user-facing documentation.
- Assistant first-send creates a conversation automatically; the conversation picker selects saved chats and App access controls tool calling. New/switch/delete-active/cancel aborts the stream and discards queued actions, but requests already sent may complete. Tool-free chat converts prior tool results into historical text; JSON completions and SSE are supported. Never send unresolved tool calls or allow queued tools to run after app access is disabled.
- Model discovery is drained in `llm_assistant::poll` every frame, not only when the assistant dock is rendered, so the main Settings tab receives model lists and errors with the dock closed.

## CI / Release

### GitHub Actions Workflows

| Workflow | Trigger | What it does |
|----------|---------|--------------|
| `ci.yml` | Push/PR to `main`/`master` | `cargo check`, `cargo test`, `cargo fmt --check`, `cargo clippy` |
| `release.yml` | Tag push (`v*.*.*`) | cargo-dist builds archives + MSI installers + DEB/RPM packages + shell/PowerShell installers, and creates the GitHub Release |

The `aarch64-apple-darwin` build is pinned to the `macos-15` runner via `[dist.github-custom-runners]` in `dist-workspace.toml` (GitHub retired dist's default `macos-14` image). DEB/RPM packaging runs only for the x86_64 Linux target. Missing package outputs
fail the workflow. Packaging reuses the `dist` profile binary instead of
rebuilding with the `release` profile. Both packages declare the dynamically
loaded Ayatana AppIndicator runtime dependency explicitly. Keep Linux system
dependencies in `dist-workspace.toml` and `ci.yml` in sync; the release workflow
also installs tray dependencies explicitly
because its cargo-dist matrix dependency-install commands are generated.
Keep `tray-icon` default features disabled: its optional `libxdo` feature is only
needed for predefined edit-menu actions, which the app does not use. Enabling it
makes Ubuntu-built RPMs require `libxdo.so.3`, unavailable on Fedora 45
(`libxdo.so.4`). Show Window/Quit and egui clipboard support do not need libxdo.

### Releasing

1. Bump version in `Cargo.toml` (and `Cargo.lock` via `cargo check`)
2. Commit and tag: `git tag v0.x.y`
3. Push tag: `git push origin v0.x.y`
4. cargo-dist creates the release automatically with all built packages.

## Known Issues & Workarounds

### Linux IME text input bug (all `TextEdit` widgets)

**Symptom:** On Linux (especially Wayland/Flatpak), every text input field in the app only accepts a single character. After typing one character, the field appears "locked" — further keystrokes are silently swallowed. Backspace and paste still work. This affects ALL text boxes (cluster filter, indices filter, console, cluster config dialog, etc.).

**Root cause:** egui's `TextEdit` widget sets `PlatformOutput::ime = Some(...)` whenever it gains focus. `egui-winit` sees this and calls `window.set_ime_allowed(true)`, activating the OS input method editor (IME). On Linux, the IME (ibus/fcitx/Wayland text-input protocol) intercepts all keyboard input and its composition state machine gets stuck after the first character — subsequent keystrokes are treated as incomplete composition events and never committed to the text buffer.

**Fix:** At the very end of `DrasticSmurfApp::update()` (in `src/app.rs`), after all UI rendering, clear the IME output so egui-winit keeps IME disabled:

```rust
#[cfg(not(target_arch = "wasm32"))]
{
    ctx.output_mut(|o| o.ime = None);
}
```

This forces text input to go through direct keyboard/character events instead of the IME pipeline, which works reliably on all platforms. CJK input methods are not supported with this workaround, but that's acceptable for an English-language Elasticsearch tool.

**Do NOT remove this line** — removing it will re-break all text input on Linux.

### Debounced text filter inputs

**Symptom:** Filter text boxes (cluster sidebar filter, indices/datastream filter) previously applied their filter on every keystroke, which caused layout thrashing and made typing feel laggy.

**Fix:** Both filter inputs now use a 300ms debounce (`FILTER_DEBOUNCE_MS` in `src/modules/indices.rs`). The textbox buffer updates instantly for smooth typing, but the actual filter is only applied 300ms after the last keystroke. The debounce decision logic (`filter_debounce_due` / `filter_debounce_remaining`) is extracted as pure, testable functions with unit tests covering no-input, within-window, boundary, past-window, and multi-keystroke-burst scenarios.

### Page-level scrolling

Every tab's content is rendered inside one vertical `ScrollArea` (`page_scroll`, salted per tab, in `DrasticSmurfApp::update`), so content that grows past the window can always be scrolled. egui still offers the inner Ui the viewport height, so modules that size panels from `ui.available_height()` fit exactly and the bar stays hidden. The page bar (and the tab bar's horizontal one) uses `ScrollStyle::solid()` so it takes its own strip instead of floating over content; nested scroll areas get the default style back. Nested areas consume the wheel only while they can still scroll, then it passes to the page.
